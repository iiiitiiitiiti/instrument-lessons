# 001. 楽器の共通契約から弦・チューニング・コードを外す

- 日付: 2026-09-10
- 対象: `src/core/lesson/types.ts` の `Instrument` 型、`src/core/` と `src/instruments/` の境界

## 背景

ウクレレ教材サイトを作るにあたり、「今後ほかの楽器も追加しうる」という前提が最初からあった。素直に設計すると、共通の楽器型に弦の数・チューニング・コード定義を持たせたくなる。

設計の途中で、次に追加する楽器が**ギターではなくオタマトーン**だと判明した。オタマトーンにはフレットがなく、音程は連続で、コードという概念も存在しない。弦を前提にした抽象化は、2つ目の楽器で即座に破綻する。

## 決定

共通の `Instrument` 型は次だけを持つ。

```ts
type Instrument = {
  id, slug, name, tagline,
  curriculum,      // レッスンの並び
  mdxComponents,   // 本文から使えるコンポーネント表
};
```

弦・チューニング・コード定義・コード図は `src/instruments/ukulele/` の中に閉じる。

依存の向きは常に「楽器モジュール → 共通基盤」の一方向。共通基盤は特定の楽器を import しない。

## 比較した代替案

- 却下: **共通契約に弦数・チューニング・コードを持たせる** — 非弦楽器で意味を成さない。オタマトーンを足す時点で型ごと作り直しになる
- 却下: **`src/kit/strings/` を先に用意し、ウクレレとギターで共有する** — 楽器が1つしかない段階で共有すべき形を推測することになり、ほぼ外す。ギターが来た時点で `ukulele/` から引き上げるほうが安い（YAGNI）
- 却下: **楽器ごとの別リポジトリ** — 改善が片方へしか反映されず、レッスン基盤・進捗・メトロノームを二重で持つ形になる
- 採用: **薄い共通契約 + 楽器モジュールへの封じ込め**

## 影響範囲

- ディレクトリ構成の全体（`src/core/` と `src/instruments/`）
- `LessonLayout` が本文コンポーネントを props で受け取る設計
- レッスン本文の解決を、楽器別の対応表ではなく `Lesson.number` からのファイル名規約で行う設計
- オタマトーン追加時に新規で要るのは「音高リボンの図」と「マイクによる音高検出」の2つだけ、という見通し

## 検証

プランAのレビュー（fable-advisor）で、初稿の `core/lesson/mdxComponents.tsx` がウクレレのコード図を import している逆依存が発見された。この判断が形だけになっていた実例で、レビュー後に修正した。

**判断が間違いだったとわかる条件:** オタマトーンを追加するとき、`src/core/` の既存ファイルに手を入れる必要が出たら、この境界の引き方が誤っている。
