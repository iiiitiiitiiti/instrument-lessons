# 007. テストは JST で走らせる

- 日付: 2026-09-10
- 対象: `vite.config.ts` の `test.env.TZ`

## 背景

進捗の日付は「利用者の手元のローカル日付」で扱う（D11）。UTC で扱うと、JST の 0〜9 時の練習が
前日として記録される。この取り違えを防ぐテストとして
`todayString(new Date(2026, 0, 1, 0, 30))` が `"2026-01-01"` を返すことを検査している。

ところが GitHub Actions のランナーは `TZ=UTC` で走る。UTC 環境では
`toISOString()` を使った誤った実装でもこのテストが通ってしまい、**CI では判別力がゼロ**になる。
ローカル（JST）でだけ効くテストは、守りたい不変条件を守れていない。

## 決定

Vitest の `test.env` で `TZ: "Asia/Tokyo"` を固定し、テスト全体を UTC 以外のタイムゾーンで走らせる。

## 比較した代替案

- 却下: **何もしない** — ローカルでは効く。ただし CI で恒真になり、UTC 実装の混入を止められない
- 却下: **CI のワークフローに `TZ` を設定する** — CI は直るが、ローカルとの差が残る。設定がワークフロー側にあると、テストがなぜ通るのかがテストのそばから読めない
- 却下: **テスト内で `vi.setSystemTime` と `vi.stubEnv` を使う** — 個別テストの意図は明確になる。だがタイムゾーンは `Intl`/`Date` の生成時に決まるため、実行時の差し替えでは端末ローカルの日付計算を再現しきれない
- 採用: **Vitest の設定でテスト全体を JST に固定する**

## 影響範囲

- 日付を扱うテストすべて。`currentStreak` は UTC ミリ秒で歩進するため影響を受けない
- 将来 UTC 前提のテストを足すときは、この固定を思い出す必要がある

## 検証

一時テストで `new Date(2026, 0, 1).getTimezoneOffset()` が 0 でないこと、
かつ `new Date(2026, 0, 1, 0, 30).toISOString()` が `2025-12-31` を返すこと（= UTC 実装なら落ちる）を実測した。
