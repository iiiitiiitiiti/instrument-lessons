# 006. 壊れた進捗は楽器ごとに捨てる

- 日付: 2026-09-10
- 対象: `src/core/progress/store.ts` の `loadProgress`

## 背景

プランAの初版の `loadProgress` は、localStorage の内容が `object` でありさえすればそのまま返していた。
`{"ukulele":{}}` のように配列が欠けた値が入ると、画面側の
`progress.completedLessonIds.includes(...)` で例外になり、コース概要とレッスンページが白画面になる。

普通の Web サイトなら利用者が DevTools で localStorage を消せる。だがこのサイトは PWA として
ホーム画面から起動する（D14）ため、白画面になった利用者には復旧手段が無い。
壊れた値が入る経路は、保存形式を変えたとき（`practiceDates` を後から足した等）と、
手で編集したときの2つ。前者は今後プランB・Cで実際に起こりうる。

## 決定

`loadProgress` は楽器ごとに形を検証し、**満たさない楽器の分だけを捨てる**。
検証するのは `completedLessonIds` と `practiceDates` が文字列の配列であること、
`lastLessonId` が文字列または `null` であること。

## 比較した代替案

- 却下: **検証しない（初版のまま）** — コードは短い。ただし壊れた値が1つ入るだけで画面が落ち、PWA では利用者が自力で直せない
- 却下: **1つでも壊れていたら全体を空にする** — 実装はさらに単純。だがウクレレの35日分の進捗が、将来追加するオタマトーンの壊れた1エントリのせいで消える。楽器ごとに独立させた設計（D1）と食い違う
- 却下: **保存形式にバージョンを持たせてマイグレーションを書く** — 正攻法だが、保存するのは短い配列3本だけ（D10）で、書くコストが釣り合わない。キー名に `:v1` が入っているため、形式を変えるときはキーを変える手も残っている
- 採用: **楽器ごとに検証し、壊れた分だけ捨てる**

## 影響範囲

- `src/pages/CoursePage.tsx` と `src/pages/LessonPage.tsx` は、`useProgress` が必ず配列を返す前提で書かれている。この前提を保つのが `loadProgress` の役目
- プランB・Cで `InstrumentProgress` に項目を足すときは、`isInstrumentProgress` の検証も足す。足し忘れると、新項目が欠けた既存の保存内容が丸ごと捨てられる

## 検証

`tests/core/progress.test.ts`「形が壊れた楽器の分だけを捨てる」で、正常な1件を残して
`{}` と `completedLessonIds: "uk-01"`（配列でない）の2件が捨てられることを検査している。

判断が間違いだったとわかるのは、捨てたことを利用者に知らせないまま進捗が静かに消えて混乱が起きたとき。
その場合は、捨てた事実を画面に出す（あるいは退避キーへ移す）ほうへ倒す。
