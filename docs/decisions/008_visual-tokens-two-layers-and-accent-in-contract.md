# 008. 視覚トークンを2層で持ち、アクセント色は楽器データに置く

- 日付: 2026-09-10
- 対象: `src/styles.css`、`src/core/lesson/types.ts` の `Instrument.accent`

## 背景

プランAは「最低限のスタイル」（45行の CSS）で公開まで通し、視覚方針はプランBで決める段取りだった。
その前にユーザーから「今のうちにもっとデザイン性を出しておいて欲しい」と指示があり、前倒しした。

仕様 §13 が制約を3つ定めている。コード図はスマホを腕を伸ばした距離で読める大きさを最優先、
ハワイアンの空気感は配色でほのかに漂わせる程度、楽器ごとのアクセントカラーをデータで持つ。
このうち3つ目を、共通契約（`Instrument` 型）に色を入れてよいのかという判断が必要になった。
弦・チューニング・コードを共通契約から外した DDR 001 と衝突しないかが論点。

## 決定

**トークンは Primitive／Semantic の2層**を CSS カスタムプロパティで持ち、画面側は Semantic だけを参照する。

**アクセント色は共通契約に置く**（`Instrument.accent`）。色は楽器の構造に依存しないため、
オタマトーンにもそのまま与えられる。画面は `style={{ "--instrument-accent": instrument.accent }}` で
1色を流し込み、濃淡は `color-mix()` で派生させる。楽器が増えても画面側のコードは変わらない。

## 比較した代替案

- 却下: **トークンを1層（用途名だけ）にする** — 記述は短い。だが「同じ意味で使っていた箇所」が
  色を見直すときに追えなくなる。ユーザーが業務で Figma のデザインシステムを
  Primitive／Semantic の2層バリアブルで組んでいるため、同じ分け方に揃えるほうが読み替えの手間がない
- 却下: **アクセント色を `src/instruments/ukulele/` に閉じる** — DDR 001 との一貫性は保てる。
  しかし色は弦やコードと違って楽器の構造に依存せず、閉じると画面側が楽器ごとの分岐を持つことになる。
  「共通契約を薄くする」の趣旨は、非弦楽器で意味をなさない概念を入れないことであって、色は該当しない
- 却下: **アクセント色を2値（base と wash）でデータに持つ** — 派生の計算が不要になる。
  ただし楽器を足す人が2色の釣り合いを毎回決めることになる。1色だけ決めれば済む形を選んだ
- 却下: **画面ごとにアクセント色を決める** — 楽器が増えたときに定義が散る
- 採用: **2層トークン＋共通契約に1色**

## 影響範囲

- 4画面（トップ・コース概要・レッスン・404）と `ChordDiagram`・`TonePlayer` の全スタイル
- 楽器を追加するときは `accent` を1つ決めるだけで、コース概要とレッスンの配色が切り替わる
- `color-mix()` に依存する。未対応のブラウザでは派生色が無効値になり、文字色は継承色で描かれる
  （読めなくはならないが、アクセントは失われる）

## 検証

- コントラスト比を実測し、WCAG 2.2 SC 1.4.3 を満たすことを確認した。
  本文 15.41:1 / 補助 5.60:1 / アクセント 5.69:1 / 白の上のアクセント 5.94:1 / 達成色 5.39:1
- 実ブラウザで `--accent` が `#1d6f6a` に解決し、色帯とボタンに反映されることを確認
- 幅 320px と 390px で横スクロールが出ないこと、押せる要素の高さが最小 56px（Apple HIG の 44px 以上）を確認

判断が間違いだったとわかるのは、2つ目の楽器（オタマトーン）を足したときに
`accent` の1色では足りず、画面側に楽器ごとの分岐が必要になったとき。
その場合は `accent` をオブジェクトへ広げる。
