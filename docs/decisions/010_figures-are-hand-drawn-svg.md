# 010. 図はすべて自作の SVG にする（写真を使わない）

- 日付: 2026-09-10
- 対象: `src/core/widgets/Figure.tsx`、`src/instruments/ukulele/widgets/figures/`

## 背景

視覚設計を入れたあと、ユーザーから「サイトの中に適宜画像入れるとかできないかなぁ」と相談があった。
本文には図があると効く箇所が具体的にある。Lesson 01 の各部の名前・弦の数え方・3フレットの意味・
右手を置く位置、Lesson 02 の弦の音の高さ。プランBのストロークやリズムも同じ。

制約が2つあった。

1. **公開先が public リポジトリの GitHub Pages** のため、Web から拾った写真は原則使えない。
   PD / CC0 / CC-BY に限られる。disney-archive では「個人利用の名鑑なら出典付きで
   自由利用不可の画像も使う」と判断したが、あれは非公開・私的利用の文脈で、ここには当てはまらない
2. **オフライン前提の PWA** のため、外部ドメインから読む画像は使えない。
   Service Worker の precache 対象はローカルの生成物だけで、外部は入らない

## 決定

**図はすべて SVG で自作し、写真を使わない。** ユーザーの選択（2026-09-10）。

図版の枠 `Figure`（キャプションと `role="img"` / `aria-label`）は楽器非依存なので `core/widgets/` に置き、
図の中身は楽器固有なので `instruments/ukulele/widgets/figures/` に置く。依存は下向きのまま（DDR 001）。

viewBox の幅は全図 320 に揃える。図ごとに変えると、図の実寸を CSS で決めている都合で
**図中の文字だけが図ごとに伸び縮みする**。実測で 320px 幅の画面で 8.6px まで落ちていた。

## 比較した代替案

- 却下: **ユーザーが自分のウクレレを撮る** — 教材としては最も説得力がある（本人の楽器そのものが写る）。
  撮影の手間が先に来るため、まず図で完結させる側を選んだ。将来足したくなったら枠を増やせばよい
- 却下: **Wikimedia Commons の PD / CC0 写真** — すぐ揃う。ただし自分の楽器ではないため、
  機種や弦の張り方（High-G / Low-G、サイズ）が本文の前提とずれうる。出典の記録も別途必要になる
- 却下: **CC-BY を含めて使う** — 選択肢は広がるが、クレジット表示の仕組みを持つことになる
- 採用: **SVG の自作のみ**

## 影響範囲

- 本文に図を足す作業がすべて「コンポーネントを書く」作業になる。プランBのストローク・リズムも同じ形で作る
- 写真を入れないため `jpg` / `webp` の precache 設定は不要。`globPatterns` は `svg,png` のままでよい
- 図が色を持たないため、アクセント色（DDR 008）にそのまま追従する
- `Figure` は `role="img"` と `aria-label` を枠側で持つ。中の SVG に持たせると読み上げが二重になる

## 検証

- 4図＋1図（Low-G 版）を実ブラウザで描画し、幅 320px / 390px / 1280px で
  はみ出しが無いこと、図中の文字が実寸 12.4px〜16px に収まることを実測
- `PitchMap` は `UKULELE_TUNING` と `noteToMidi` から高さを計算する。
  図に数値を書き写すと、チューニングを変えたときに図だけが古くなるため
- `tests/ukulele/lessonRender.test.tsx` で本文を実際に描画する。
  MDX は未登録のコンポーネントを本文で使うと例外を投げるので、登録漏れがこの検査で落ちる。
  未登録の図を本文へ足してテストが落ちることを実測で確認した

判断が間違いだったとわかるのは、木目や手の形のように「実物がどう見えるか」を
図で代用できない箇所が出てきたとき。その場合はユーザー撮影の写真を足す（枠は既にある）。
